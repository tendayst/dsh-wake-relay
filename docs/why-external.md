# 为什么把判断放在宿主外面

DSH 的插件生态里，「唤醒 agent」这个需求已经有几个实现。它们的共同结构是：

```
插件加载 → 定时器 → 探针 → 条件成立 → followup() 唤醒
```

全部跑在宿主进程里。这在 90% 的场景下够用，但有三种情况会漏：

| 情况 | 宿主内探针的结果 |
|---|---|
| DSH 重启（升级、崩溃、你手动关了） | 计时器消失；这期间到达的条件不再被观察 |
| 条件成立后又消失（数值穿过阈值又回来、文件写了又删、任务失败后被自动重试成功） | 窗口内的那个边沿永久丢失 |
| 你需要「即使 agent 不在也要有人记着这件事」 | 没人记着 |

根因不是实现质量，是**故障域**：探针和宿主共享同一个生命周期，宿主挂则探针挂。再多的重试逻辑也救不回来，因为重试代码本身也在那个进程里。

## 拆成两半

```
┌──────────── 外部进程（你自己的） ────────────┐
│  探测 30s 一轮                               │
│  条件成立 → 事件进本地持久化队列              │
│  POST /wake（幂等 event_id）                 │
│  503 → 留在队列，TTL 内重试   ← 关键         │
└──────────────────────────────────────────────┘
                    │ HTTP 127.0.0.1
┌──────────── 宿主进程（插件） ────────────────┐
│  验证 token                                  │
│  去重 / per-reason 限流                      │
│  resolveAgent → followup → flush             │
│  200 仅在此后返回；失败不记账                 │
└──────────────────────────────────────────────┘
```

拆开之后，两个进程各自拥有独立的重启周期：

- 宿主挂了：外部进程照常采样，事件排队，等宿主回来补投。
- 外部进程挂了：插件不受影响，宿主里已有的唤醒照常投递。
- 两个都挂了：事件在外部进程的磁盘队列里，TTL 内起来就能补。

## 那个 200/503 约定是全部的关键

如果插件在「投递成功之前」就返回 200，调用方会认为事情办完了，事件就永久丢了。反过来如果失败时也记账（写进去重表），重试就会被判成 duplicate，也永久丢。

所以：

- **200** 只在 `flush()` 真的返回之后发。
- **503** 只在「什么都没发生」时发——不写去重表、不写限流窗口、不写日志之外的任何东西。
- **429** 才是「按策略丢掉了」，明确告诉调用方别重试。

这三条让重试成为纯安全操作：用同一个 `event_id` 重发，最多成功一次。

## 代价

1. 你得有一个常驻的外部进程。本包的 `watcher/` 是给这个用的，但任何脚本都行。
2. 两段式意味着两个失效点——外部进程死了，唤醒就停了。所以它必须由计划任务/服务托管，并且要能自报状态（`GET /status` 会折叠外部 watcher 的队列摘要）。
3. 判断逻辑不在模型手里。条件写死在规则表里；需要「看到条件后再判断」的场景，应该只把「条件成立」这个事实送进来，让会话去决定做什么——规则里不要写死结论。

## 不该用它的时候

- 纯时间（3 小时后、每天 9 点）：用原生 `schedule`。它持久化、停机后补发、不占进程。
- 需要毫秒级闭环的动作（实时控制、硬件回环、执行层动作）：交给专门的执行系统，别经过一个模型。延迟、成本、可靠性都差三个数量级。
- 想在会话里「等一会儿再看」：那是宿主内的活，别跨进程。
